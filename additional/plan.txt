1.  Product Overview
A web-based AI sprint planning assistant for small software teams (5-15 people). The user configures their team once, pastes their backlog as epics, selects a domain, and receives a full sprint plan - broken into user stories and tasks, estimated in Fibonacci story points, and assigned to developers within real capacity limits.

The system supports two entry modes:
ï Fresh Start - no prior history. The system uses conservative defaults and begins building memory from the first sprint review.
ï Continuous Mode - existing team with sprint history. The system automatically loads two memory sources (preference profile + sprint reference) and uses them to calibrate every agent.

Before anything is pushed to Trello, the user reviews and edits the plan in a dedicated Review Screen. Every edit is logged and fed back into the preference profile, and every sprint outcome feeds the reference history - making the plan smarter over each cycle.

3.  The Four Agents
Each agent has a single responsibility. The Orchestrator calls them in sequence and validates the output of each before passing it to the next. If any agent fails, the pipeline halts and returns a structured error - no silent failures.

Agent 1 - BreakdownAgent

BreakdownAgent
Role
Converts each epic into user stories, then breaks each user story into concrete development tasks with acceptance criteria.
Input
Epic title + description ∑ Domain ∑ Sprint goal ∑ Team roles ∑ Definition of Done ∑ team_profile.md (preference) ∑ sprint_history.md (last 3 sprints, if available)
Output
Structured list of user stories, each with 2-4 child tasks. Each task has: title, description, acceptance criterion, role tag (backend / frontend / qa / devops).

Pseudocode:
FUNCTION breakdown(epic, context):
    prompt = build_prompt(epic, context.domain, context.sprint_goal,
                         context.definition_of_done,
                         context.preferences,      // from team_profile.md
                         context.sprint_history)   // from sprint_history.md
    raw = call_llm(prompt)
    stories = parse_user_stories(raw)
    FOR EACH story IN stories:
        validate: has title, has 2+ tasks, each task has acceptance_criterion
        IF invalid: retry once with correction prompt
    RETURN stories

Note: Epic ? User Story ? Task (3-level breakdown). Both memory sources fed into prompt.

Agent 2 - EstimationAgent

EstimationAgent
Role
Assigns a Fibonacci story point value to each task using domain context and task complexity signals. Validates every value against the allowed set.
Input
Task list from BreakdownAgent ∑ Domain ∑ Sprint goal ∑ velocity_history from sprint_history.md (actual vs planned per task type)
Output
Same task list with story_points field added. Every value is in {1, 2, 3, 5, 8, 13}. Tasks with 8 or 13 points are flagged for PM review.

Pseudocode:
FUNCTION estimate(tasks, context):
    FOR EACH task IN tasks:
        prompt = build_estimation_prompt(task, context.domain,
                                         context.velocity_history,
                                         context.estimation_errors)  // from sprint_history.md
        raw_points = call_llm(prompt)
        points = round_to_fibonacci(raw_points)
        IF points NOT IN {1,2,3,5,8,13}: points = nearest_fibonacci(raw_points)
        IF points >= 8: flag_for_review(task)
        task.story_points = points
    RETURN tasks

Note: Large tasks (8, 13 pts) are surfaced on the Review Screen as "consider splitting." Estimation errors from past sprints are also injected, letting the agent self-correct known biases.

Agent 3 - CapacityAgent

CapacityAgent
Role
Pure algorithm - no LLM call. Computes each developer's real available story point budget for this sprint.
Input
Developer list (name, role, base_velocity) ∑ Sprint length in days ∑ days_off per developer ∑ Historical completion rate from sprint_history.md
Output
Capacity map: { developer_id ? available_story_points }

Pseudocode:
FUNCTION calculate_capacity(developers, sprint_days, history):
    FOR EACH dev IN developers:
        working_days = sprint_days - dev.days_off
        base_capacity = working_days * (dev.base_velocity / sprint_days)
        IF history[dev.id] EXISTS:
            completion_rate = history[dev.id].avg_completion_rate
            adjusted = base_capacity * completion_rate
        ELSE:
            adjusted = base_capacity * 0.80  // conservative default (fresh start)
        capacity_map[dev.id] = floor(adjusted)
    RETURN capacity_map

Agent 4 - DistributionAgent

DistributionAgent
Role
Assigns tasks to developers. LLM ranks fit (role match, workload balance, past preference and past performance); algorithm enforces hard capacity constraints.
Input
Estimated task list ∑ Capacity map ∑ Developer roles ∑ team_profile.md (preference) ∑ sprint_history.md (per-developer performance by task type)
Output
Final sprint plan: each task has assigned_developer, story_points, sprint_id. Unassigned tasks flagged.

Note: Unassigned tasks are surfaced on the Review Screen. PM can manually assign or defer to next sprint.

4.  Review Screen
The Review Screen is the most important feature. Nothing is pushed to Trello until the user approves. This single step solves the trust problem: users stay in control, bad AI outputs are caught before they matter, and every edit becomes preference training data.

Standard actions
ï Edit any field inline (title, points, assignee)
ï Drag task to different developer
ï Delete task or add a custom task
ï Mark task as "defer to next sprint"
ï Approve ? push to Trello

Mismatch Warnings (Continuous Mode only)
When sprint_history.md shows a consistent gap between what was planned and what was actually delivered, the Review Screen surfaces it explicitly - it does not silently adjust. This is the kind of insight an experienced PM gives in a retrospective. The system gives it automatically.

Examples of surfaced warnings:

Warning Type
Example Message
Velocity mismatch
??  Your team planned 50 pts last 3 sprints but completed 35 on average. This plan is 48 pts - consider deferring lower-priority tasks.
Estimation drift
??  'Analytics tracking' tasks have been underestimated 3 sprints in a row. Suggested: +2 pts on each.
Assignment risk
??  Ceren is assigned 13 pts this sprint. Her 3-sprint average is 9 pts completed. Consider redistributing 4 pts.
Goal miss pattern
??  Sprint goal was 'Partially' or 'No' last 2 sprints. The team may be over-committing on scope.

The PM can dismiss any warning. Dismissed warnings are logged but do not affect the preference profile.

5.  Preference Memory (Edit-Based)
Every change the user makes on the Review Screen is logged as a diff. After the session, PreferenceService aggregates diffs into a team_profile.md. This file captures intent - what the team's PM explicitly chose to override.

How it works
ï User edits task on Review Screen (rename, re-estimate, reassign)
ï EditLogger records the diff: { field, original_value, new_value, task_type, domain }
ï After approval, PreferenceService aggregates diffs into team profile
ï Profile stored as structured JSON and rendered to readable Markdown
ï On next sprint: team_profile.md injected into BreakdownAgent, EstimationAgent, DistributionAgent prompts

Example team_profile.md
# Team Preferences - Trendyol Checkout Squad

## Estimation
- Payment-related tasks: user consistently raises to 5+ pts
- Analytics/tracking tasks: user consistently lowers to 1-2 pts

## Assignment
- Backend API tasks: prefer Ahmet or Buse (never Ceren)
- Mobile tasks: always assign to Ege

## Task Breakdown
- Auth epics always need an extra 'write integration tests' task

Preference memory is intent. It reflects what the PM decided to do. It does not track whether those decisions led to good outcomes - that is the job of reference memory (Section 7).

6.  Sprint Review & Velocity Learning
After the sprint ends, the user closes it via a simple form. This data feeds directly into CapacityAgent for the next sprint and is the primary input to the ReferenceBuilder service (Section 7).

Field
Description
Task completion
Done / Not Done toggle per task
Sprint goal result
Did the team hit the sprint goal? Yes / Partially / No
Blocker note
Optional free-text: what blocked the sprint?
Developer actuals
Actual story points completed per developer (auto-calculated from task toggles)

What happens with this data:
ï completion_rate per developer = tasks_done / tasks_assigned (by story points)
ï CapacityAgent uses this rate next sprint to adjust individual budgets
ï Developers who consistently over/underdeliver get realistic capacity automatically
ï Sprint goal result stored - shown in team dashboard over time
ï All data passed to ReferenceBuilder ? sprint_history.md updated

7.  Reference Memory (Outcome-Based)
Reference memory is distinct from preference memory. Preference captures intent (what the PM chose). Reference captures reality (what actually happened). Sometimes they conflict - a team may keep planning 50 pts while consistently completing 35. That tension is surfaced to the PM, not silently resolved.

ReferenceBuilder Service
ï Triggered automatically after each Sprint Review Form submission
ï Reads sprint outcome JSON and appends to sprint_history.md
ï Maintains a rolling 3-sprint window - older sprints are archived but not injected into prompts
ï 3-sprint cap is intentional: recent patterns matter more than history; keeps prompt size bounded

9.  Domain Context System
